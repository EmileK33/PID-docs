#### S1-A — DB Models & Migrations

**Phase 1 | Infrastructure | Needs: S0-A, S0-B**

##### Objective

Define all SQLAlchemy ORM models and Alembic migrations for the PID Analyzer's PostgreSQL schema, including RLS policies, audit log partitioning, and seed data for tiers and entity classes — establishing the persistence foundation every backend service in Phase 2 depends on.

##### Scope

P0 MVP — all tables in §1.2 are required for MVP. Tables that primarily support P1 features (`team`, `team_id` columns on `user`/`subscription`/`drawing`, `revision_comparison`, `table_cell`) MUST still be created at MVP migration time since the schema is monolithic and the columns are referenced by FK constraints elsewhere; P1 application logic against them is stubbed in other sessions, not here.

##### Technology constraints

- **PostgreSQL** (RDS/Aurora target; local Postgres 15+ for tests). ACID, JSONB for bbox payloads, RLS, partitioning.
- **SQLAlchemy 2.x** (declarative typed models) — must be used for ORM definitions.
- **Alembic** for migrations; `backend/alembic.ini` and `backend/alembic/env.py` are pre-stubbed by S0-A.
- **`pgcrypto` extension** required (for `gen_random_uuid()`).
- MUST NOT use: any other ORM (Django ORM, Tortoise, Peewee); raw `psycopg` cursor-only patterns; UUID generation in application code where the schema specifies `DEFAULT gen_random_uuid()`.
- MUST NOT depend on PgBouncer-incompatible features (no server-side prepared statement caching that breaks with transaction pooling).

##### Performance targets

None directly owned at the model/migration layer. Indexes specified in §1.2 are load-bearing for downstream SLAs:
- `idx_drawing_team_state_date` and `idx_drawing_user` — support the <2s P95 Drawing Library load (owned by S2-B).
- `idx_detected_symbol_drawing_rejected_class` and `idx_detected_symbol_drawing_page` — support <3s P95 canvas symbol fetch (owned by S2-C).
- `idx_drawing_fts` (GIN tsvector) — supports Library search (owned by S2-B).
- `idx_user_correction_consent` (partial index) — supports ML training data extraction (P1).

This session's responsibility: ship those indexes verbatim. No SLA monitoring is owned here.

##### Critical implementation notes

- **§1.4 rule 11 (GDPR anonymous_id ordering)** — paste verbatim: *"On first erasure job execution, the computed anonymous ID is written to `USER.anonymous_id` before any records are updated. All subsequent erasure job retries... read `USER.anonymous_id` directly."* Implication for this session: `user.anonymous_id` MUST be NULLable VARCHAR. Do not add a NOT NULL constraint. Do not add a default.
- **§1.4 rule 10 (Stripe idempotency)** — paste verbatim: *"Idempotency enforced via Stripe event ID stored in DB before any state mutation."* Implication: `stripe_event.id` is the Stripe-supplied string event ID and is the primary key (a unique constraint alone is insufficient under concurrent INSERT races since the consumer relies on PK conflict for atomic idempotency).
- **§1.4 rule 5 (user_id at enqueue)** — `drawing.owner_user_id` and `drawing.owner_team_id` are nullable individually but XOR-constrained via `CHECK (drawing_owner)`. The constraint name `drawing_owner` is load-bearing; downstream consent and worker code may reference it in error parsing. Use exactly that name.
- **XOR constraints are load-bearing** — `subscription_user_or_team`, `drawing_owner`, `consent_user_or_team`, `correction_symbol_or_cell`. Constraint names must match §1.2 verbatim.
- **CASCADE deletes**: `detected_symbol.drawing_id` and `table_cell.drawing_id` use `ON DELETE CASCADE`. `user_correction`, `export_record`, `revision_comparison` do NOT cascade — they retain referential integrity for audit/training data. Honor this exactly; getting it wrong silently corrupts the GDPR erasure pipeline (which relies on anonymization, not cascade).
- **FTS index on `drawing`**: `CREATE INDEX idx_drawing_fts ON drawing USING GIN (to_tsvector('english', filename || ' ' || COALESCE(revision_label, '')));` — must use exactly this expression; S2-B's search query depends on it being a functional index over `to_tsvector('english', ...)` with the COALESCE form.
- **Partial index on `user_correction(training_consent) WHERE training_consent = TRUE`** — load-bearing; required for efficient ML training data extraction. Do not replace with a full index.
- **`audit_log` is RANGE-partitioned by `occurred_at`** — primary key is composite (`id`, `occurred_at`) because Postgres requires the partition key to be part of any unique constraint on a partitioned table. Migration `0003_audit_partitions.py` MUST create the parent table with `PARTITION BY RANGE (occurred_at)` and create the rolling monthly partitions for at minimum: the current month and the next month at migration time. Provide a helper function `create_audit_log_partition(year: int, month: int)` in `backend/app/db/models/audit_log.py` that downstream operational tooling can invoke. Naming convention: `audit_log_YYYY_MM`.
- **RLS enablement is in a separate migration (`0002_rls_policies.py`)** — enable RLS on the five tables listed in §1.2. Per §1.2: *"enforce ownership server-side in middleware as primary control"*. Therefore: enable RLS but DO NOT add row-level policies in this session (no `CREATE POLICY` statements). The middleware (S1-B) is the primary control; RLS-enabled-without-policy is a defense-in-depth posture that prevents accidental superuser-context reads from bypassing the design. The Alembic migration must use `FORCE ROW LEVEL SECURITY` so that the table owner is also subject (since application connections may run as table owner in some deploy configurations).
- **`pgcrypto` extension** must be created in migration `0001_initial_schema.py` BEFORE any table creation that uses `gen_random_uuid()`.
- **Seed data is run via Alembic, not application startup** — embed `seed_tiers` and `seed_entity_classes` content as INSERTs inside migration `0001_initial_schema.py` (use `op.bulk_insert` or raw `op.execute`). The Python files `seed_tiers.py` and `seed_entity_classes.py` exist as the source-of-truth data structures importable by tests, but the migration itself must INSERT the rows so a fresh DB is fully populated by `alembic upgrade head` alone. Failure mode if violated: a fresh prod deploy has no `tier` or `entity_class` rows and every drawing INSERT fails on FK.
- **Entity class seed values** must use exactly the `EntityClassId` literal members (`pipe`, `valve_gate`, `valve_globe`, `valve_ball`, `valve_butterfly`, `valve_check`, `valve_control`, `instrument`). Use the color hex values: `pipe`=`#1f77b4`, valves family=`#d62728`, `instrument`=`#2ca02c`. Set `parent_class` to `valve` for all `valve_*` rows; NULL for `pipe` and `instrument`. (Color spec is the canonical color-coded overlay scheme; downstream canvas rendering reads `entity_class.color_hex`.)
- **`"user"` is a reserved word in PostgreSQL** — the SQL identifier MUST be quoted. In SQLAlchemy: `__tablename__ = "user"` works; for FKs use `ForeignKey('"user".id')` with the double-quotes preserved, or use `ForeignKey('user.id')` and rely on the dialect to quote — verify by inspecting generated DDL.
- **Avoid**: do NOT use `sqlalchemy.types.Enum` for the CHECK-constrained string columns. Use `String` + `CheckConstraint`. Reasons: (a) §1.2 spec uses CHECK constraints; (b) `Enum` creates a Postgres `TYPE` which makes migrations involving new states require type-altering migrations that interact badly with rolling deploys.
- **`bbox` columns** are `JSONB NOT NULL`. The application-level shape is `{ x, y, w, h }` (BoundingBox in §1.1) but the DB stores opaque JSONB — do not constrain at the column level.
- **Confidence range**: `CHECK (confidence >= 0 AND confidence <= 1)` — name this constraint `detected_symbol_confidence_range` for traceability.
- **Cross-session contract**: every model class and the `Base` re-export must be importable from `backend.app.db.models` (the `__init__.py` re-exports everything). S1-B, S2-A through S2-M, and S2-H through S2-M all import from this path. The set of class names is `[LOAD-BEARING]` and listed in Output and handoff.
